# TradeLog

> 매매 기록과 복기를 통해, 나의 투자 판단과 습관을 데이터로 돌아보는 개인 매매일지 웹 애플리케이션입니다.

## 프로젝트를 만든 이유

저는 국내 주식에 투자하면서 재무제표를 살펴보고 매수했는데도, 매수한 뒤 주가가 하락하는 경험을 반복했습니다. 매매 당시에는 나름의 근거가 있었지만 시간이 지나면 왜 매수했는지, 어떤 상황을 예상했는지, 결과를 보고 무엇을 느꼈는지 정확히 기억하기 어려웠습니다.

그래서 매매 과정을 일기처럼 남겨보면 어떨까 생각했습니다. 거래의 가격과 날짜뿐 아니라 매수 이유와 복기 내용을 기록하고, 기록이 쌓인 뒤 다시 살펴보면 제가 반복하는 판단이나 행동을 발견할 수 있을 것이라 기대했습니다.

TradeLog는 그런 기록을 모아 투자 판단을 되짚고 개선할 근거를 마련하기 위해 만들었습니다. 기록과 분석이 수익이나 주가 상승을 보장하는 것은 아니지만, 기억에만 의존하던 매매 복기를 데이터에 기반한 과정으로 바꾸는 것이 프로젝트의 출발점입니다.

## 프로젝트 목표

- 매매 결과와 당시 판단의 이유를 함께 기록합니다.
- 누적된 거래를 종목·기간·매매 원칙 기준으로 다시 살펴봅니다.
- 손익뿐 아니라 내가 세운 원칙을 지켰는지도 확인합니다.
- 기록을 통해 반복되는 매매 습관을 발견하고 이후 판단에 참고합니다.

## 주요 기능과 설계 목적

| 기능 | 이 기능을 넣은 이유 |
|---|---|
| 매매일지 등록·조회·수정·삭제 | 거래의 가격과 날짜뿐 아니라 매수 이유와 복기 내용을 보존해 결과의 맥락까지 되돌아볼 수 있도록 합니다. |
| 종목·기간 검색, 정렬, 페이징 | 기록이 많아져도 원하는 거래를 찾고, 매도일이나 수익률 기준으로 과거 기록을 비교할 수 있도록 합니다. |
| 대시보드 | 총 거래 수, 실현손익, 평균 수익률, 승률, 원칙 준수율과 최근 거래를 한눈에 확인합니다. |
| 매매 원칙 관리 | 사용자가 중요하게 생각하는 기준을 등록하고 거래에 적용해 원칙을 거래 기록과 연결합니다. |
| 거래별 원칙 준수 여부 기록 | 수익 여부와 별개로 각 거래에서 원칙을 지켰는지 남겨 매매 과정을 함께 평가합니다. |
| 월별·종목별·원칙별 성과 분석 | 특정 기간이나 종목, 원칙에 따라 결과가 어떻게 달라지는지 살펴볼 수 있도록 합니다. 준수 거래와 미준수 거래 비교도 제공합니다. |
| 종목 검색·현재가 참고 | 종목 입력을 돕고 매도가와 현재가를 비교해 매도 이후의 가격 변화를 복기할 때 참고할 수 있도록 합니다. |

성과 분석은 특정 원칙이 수익의 원인이라고 증명하기 위한 기능이 아니라, 개인 거래 기록에서 반복되는 경향을 살펴보기 위한 기능입니다.

## 애플리케이션 구조와 기술 선택

TradeLog는 브라우저의 화면 요청을 Spring MVC Controller가 받고, Service의 업무 처리와 MyBatis Mapper의 데이터 접근을 거쳐 Oracle에 저장하는 구조입니다.

```text
Browser
  ↓
Controller  ── 요청 파라미터·세션·화면 응답
  ↓
Service     ── 입력 검증·업무 처리·계산·소유권 확인
  ↓
Mapper      ── MyBatis SQL 실행
  ↓
Oracle Database
```

Controller, Service, Mapper의 책임을 나눈 이유는 화면 요청 처리, 매매 업무 규칙, SQL을 구분해 기능의 흐름과 변경 지점을 파악하기 쉽게 하기 위해서입니다. 개인용 매매일지의 도메인과 규모를 여러 독립 서비스로 나눌 필요가 없다고 판단해, 한 애플리케이션 안에서 기능 전체를 처리하는 구조를 선택했습니다.

| 기술·구조 | 선택 이유와 고려한 점 |
|---|---|
| Java 11 | Java 11을 기준으로 구현합니다. 거래 가격과 손익 계산에는 `BigDecimal`, 거래일에는 `LocalDate`를 사용해 금액과 날짜를 다룹니다. |
| Spring Framework 5.3.39 / Spring MVC | JSP 기반 웹 애플리케이션을 MVC 구조로 구성합니다. 사용자의 요청이 `DispatcherServlet`을 거쳐 Controller, Service, Mapper로 이어지고 다시 화면으로 응답되는 흐름을 직접 구현하며 각 계층의 역할을 이해하는 것을 목표로 했습니다. XML 기반 설정과 인터셉터, ViewResolver, Bean 연결도 직접 확인할 수 있습니다. |
| JSP / JSTL | 서버에서 조회한 데이터를 화면에 렌더링합니다. 매매일지와 분석 기능을 서버 중심의 요청·응답 흐름으로 구현해 Spring MVC와 화면의 연결을 함께 살펴볼 수 있습니다. |
| MyBatis 3.5.16 | JPA는 엔티티와 객체를 중심으로 데이터 접근을 추상화하고 기본적인 SQL 생성을 ORM에 맡길 수 있는 반면, MyBatis는 개발자가 SQL을 직접 작성해 Mapper에 연결합니다. TradeLog에서는 종목·기간 검색, 정렬·페이징, 성과 집계 쿼리를 눈으로 확인하고, SQL 결과가 DTO와 화면으로 전달되는 흐름을 이해하고 싶어 MyBatis를 선택했습니다. 그 대신 SQL과 Mapper XML을 직접 관리해야 합니다. |
| Oracle Database | 회원, 거래, 원칙, 거래별 원칙 체크의 관계를 기본키·외래키·제약조건으로 표현하고, 거래 데이터를 검색·집계합니다. |

## 데이터베이스 설계

거래와 원칙을 분리한 이유는 한 거래에 여러 원칙을 적용할 수 있고, 하나의 원칙을 여러 거래에서 재사용할 수 있기 때문입니다. 준수 여부는 거래와 원칙의 관계마다 달라지므로 `TRADE_RULE_CHECK`에 저장합니다.

| 테이블 | 역할 |
|---|---|
| `MEMBER` | 로그인 계정과 회원 정보를 저장합니다. |
| `TRADE` | 회원별 종목, 매수·매도 정보, 매수 이유와 복기 내용을 저장합니다. |
| `TRADE_RULE` | 회원이 등록한 재사용 가능한 매매 원칙을 저장합니다. |
| `TRADE_RULE_CHECK` | 거래와 원칙을 연결하고 해당 거래에서의 준수 여부(`Y`/`N`)를 저장합니다. `(TRADE_ID, RULE_ID)`를 복합 기본키로 사용합니다. |

실현손익과 수익률은 매수가·매도가·수량으로 계산되는 값이므로 거래 입력 데이터와 분리된 별도 테이블에 저장하지 않습니다. 거래와 원칙의 다대다 관계 및 회원과 거래·원칙의 관계는 아래 ERD에서 확인할 수 있습니다.

## 트러블슈팅

### 정렬 조건을 안전하게 처리하기

**상황:** 거래 목록의 정렬 기준은 URL 요청 파라미터로 전달됩니다. 정렬을 동적으로 처리할 때 요청 문자열을 SQL에 직접 삽입하는 방식은 피해야 합니다.

**위험:** MyBatis의 `${}`처럼 문자열을 그대로 치환하는 방식을 사용하면 임의의 SQL 조각이 정렬식에 삽입될 수 있습니다.

**해결:** `TradeSearchCondition`에서 `oldest`, `returnDesc`, `returnAsc`만 허용하고, Mapper에서는 미리 정의한 정렬 조건 중 하나를 선택합니다. 허용되지 않은 값은 기본 정렬로 처리하며, 예상 밖의 정렬 값이 허용 목록에서 제외되는지 테스트합니다.

### 페이지 이동 중 검색 조건 유지하기

**상황:** 종목명·기간·정렬 조건으로 검색한 뒤 다음 페이지로 이동해도 같은 조건으로 결과를 이어서 봐야 합니다.

**해결:** 페이지 이동 링크에 `keyword`, `startDate`, `endDate`, `sort`를 함께 전달합니다. JSP의 URL 생성과 출력에는 JSTL을 사용해 링크를 구성하고 요청 값을 화면에 출력할 때 이스케이프합니다.

## 회고

TradeLog를 시작할 때는 매매일지를 꾸준히 쓰고 기록을 쌓으면 제 투자 판단도 나아질 수 있지 않을까 기대했습니다. 기능을 구체화하면서 단순히 거래 결과를 저장하는 것만으로는 매매 당시의 생각을 되짚기 어렵다는 점을 고려해, 매수 이유와 복기 내용, 매매 원칙 준수 여부도 함께 기록하도록 설계했습니다.

구현 과정에서는 화면 요청이 Controller에서 Service와 Mapper로 이어지는 흐름, 검색 조건과 SQL의 연결, 사용자별 데이터 소유권 확인, Oracle의 관계와 제약조건을 함께 다뤘습니다. 이를 통해 기능을 구현하는 것뿐 아니라 각 계층이 맡는 책임과 데이터가 화면에 도달하는 과정을 이해할 수 있었습니다.

아직 기록과 분석이 실제 투자 판단을 얼마나 개선하는지는 장기간 사용하며 확인해야 합니다. 앞으로는 UI 정의와 화면을 문서화하고, 누적된 매매 기록을 더 읽기 쉽게 확인할 수 있도록 화면과 분석 기능을 다듬고 싶습니다.
